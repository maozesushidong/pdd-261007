# 拼多多工单业务流程

## PDD slow dual-branch rules (current)

- PDD actions use `PDD_ACTION_DELAY_MS=6000`; query/detail/logistics/submit settle defaults are `8000/10000/8000/15000ms`. Chromium `slowMo` is `0` so delays are controlled in one business queue.
- The resolution page is classified from visible controls, never from the order number. For in-transit refunds, visible refund results use `已同意退货退款` -> `同意退款` -> `同意消费者退款申请`; OMS/TMS processing before this page is unchanged.
- If none of those three in-transit refund results is visible, the existing reason and intercept-progress stages continue: TMS success maps to `快递已拦截成功`, processing maps to `快递还在拦截中`, and failure/unavailable/already-signed maps to `快递拦截失败`. The processing branch waits 12 hours before selecting `消费者超12小时未回复`.
- A prior `submitting` state gets one delayed detail-state recheck. If it remains pending, it is blocked permanently for this run and the browser stays open.
- TMS evidence is `unused` for the primary branch and `used` after a successful subjective-branch upload. Either image is deleted only after PDD completion is confirmed; failed upload, failed submit, verification, rate limiting, or uncertain state retains the file.

## 1. 业务目标

每个店铺使用一个独立且常驻的 Playwright Chromium 完成以下流程；本地调试使用可见窗口，Ubuntu 24.04 生产环境使用虚拟显示器上的可远程维护有界面模式。每个店铺浏览器内部固定保留拼多多、OMS、TMS 三个已登录基准标签页，并允许临时派生工单详情、订单明细和弹窗标签：

1. 恢复或完成拼多多商家后台登录。
2. 进入“售后管理 -> 工单管理”。
3. 查询指定订单，或选择一张“订单问题：在途无理由退款处理”待处理工单。
4. 点击“立即处理”进入工单详情。
5. 读取并保存订单编号，作为后续系统的业务主键。
6. 展开发货物流，判断发货城市、当前城市以及是否已超出发货市区。
7. 对工单右侧完整详情做元素截图，临时保存为 PNG，供后续系统使用。
8. 登录 OMS，用保存的拼多多订单编号查询订单。
9. 读取当前订单行的已有标记，并进入首个 OMS 订单号的发货信息。
10. 判断指定仓库、低值品和补发单，保存结果。
11. 按 OMS 仓库与拼多多快递类型判断是否允许自动进入 TMS；不满足条件时记录 `manual-review-required` 并停止。
12. 在 TMS 客服登记中查重、自动带出订单、选择物流问题、填写客服备注、上传拼多多截图并创建工单。
13. 按交易号定位刚创建的 TMS 行，截取“交易号”至“客服备注”区域；验证成功后删除已消费的拼多多临时截图。
14. 返回同一店铺的拼多多标签页；在途退款按页面可见的三个退款结果固定优先级选择并自动提交，其他场景使用各自既有规则。
15. TMS 截图如果未用于拼多多，则在拼多多工单明确完结后删除；失败、暂停或状态不确定时保留。
16. 明确不创建 TMS 工单的场景（当前包括“异常网点预警”）仍读取并复查拼多多实际发货状态，但不生成仅供 TMS 使用的拼多多详情截图，避免每轮无用途的截图和磁盘写入。

## 2. 代码入口和店铺隔离

- 多店铺启动器：`run-shops.mjs`
- 非敏感店铺配置：`shops.config.json`
- 单店铺主流程：`workflow.mjs`
- 可视化规则：`.codex/playwright-visualization.md`

`run-shops.mjs` 为每个启用店铺启动一个独立 Node 子进程和 Chromium。不同店铺不得共享 Browser、Context、Cookie、进度、锁或截图；同一店铺的拼多多、OMS、TMS 使用一个 BrowserContext 内的三个长期基准标签页，详情和弹窗可在同一 Context 中派生额外标签。`login.mjs` 和 `work-order.mjs` 不再作为业务入口。

Linux 服务器默认数据目录为：

```text
/var/lib/pdd-workflow/shops/<shopId>/
├── auth/
│   ├── pdd-auth.json
│   ├── jeoms-auth.json
│   └── tms-auth.json
├── state/
│   ├── workflow-progress.json
│   └── completed-work-orders/<订单编号>.json
├── locks/workflow.lock
├── tmp/
│   ├── tms-logistics-work-orders/
│   └── pdd-work-order-replies/
└── diagnostics/
```

服务器目录必须归非 root 运行用户所有；可通过 `WORKFLOW_DATA_ROOT` 修改多店铺根目录。Windows 默认使用 `.codex/shops/<shopId>`。原单店铺数据只复制到配置了 `migrateLegacy=true` 的店铺目录，源文件保留。

## 3. 输入参数

| 环境变量 | 用途 | 默认值 |
| --- | --- | --- |
| `WORKFLOW_SHOP_ID` | 当前子进程的稳定店铺标识 | `default`（仅兼容旧单店铺入口） |
| `WORKFLOW_DATA_ROOT` | 多店铺数据根目录 | Linux 为 `/var/lib/pdd-workflow`；Windows 为 `.codex` |
| `WORKFLOW_DATA_DIR` | 当前店铺独立数据目录，由启动器设置 | `<数据根>/shops/<shopId>` |
| `PDD_WORK_ORDER_TITLE` | 当前店铺允许处理的精确工单标题 | `订单问题：在途无理由退款处理` |
| `<PDD_SECRET_PREFIX>_ACCOUNT` | 启动器读取的店铺拼多多账号 Secret | 无 |
| `<PDD_SECRET_PREFIX>_PASSWORD` | 启动器读取的店铺拼多多密码 Secret | 无 |
| `PDD_ACCOUNT` | 子进程内的当前店铺账号，不直接用于多店铺父进程配置 | 无 |
| `PDD_PASSWORD` | 子进程内的当前店铺密码 | 无 |
| `PDD_ORDER_NUMBER` | 指定要查询的订单编号；不设置时按工单类型选择 | 无 |
| `PDD_ACTION_DELAY_MS` | 拼多多关键业务动作的最小间隔 | `6000` |
| `PDD_QUERY_SETTLE_MS` | 拼多多查询结果稳定等待 | `8000` |
| `PDD_DETAIL_SETTLE_MS` | 拼多多详情页稳定等待 | `10000` |
| `PDD_LOGISTICS_SETTLE_MS` | 拼多多物流展开稳定等待 | `8000` |
| `PDD_SUBMIT_SETTLE_MS` | 拼多多提交后状态确认等待（最多 30 秒） | `30000` |
| `PDD_RATE_LIMIT_WAIT_MS` | 平台限流后的等待时间 | `180000` |
| `OMS_READY_TIMEOUT_MS` | OMS SPA 等待登录表单或业务菜单就绪的最长时间 | `90000` |
| `OMS_READY_POLL_MS` | OMS 就绪状态轮询间隔 | `1000` |
| `WORKFLOW_BROWSER_MODE` | `headed` 为本地可视化，`server-headed` 为服务器虚拟显示器，`headless` 仅作无人值守诊断 | `headed` |
| `PDD_EMPTY_QUEUE_POLL_MS` | 待处理队列为空后的轮询间隔 | `300000` |
| `WORKFLOW_AUTH_HEALTH_CHECK_MS` | 兼容旧配置；当前不启用 OMS/TMS 周期刷新，仅在实际操作前检查 | `900000` |
| `WORKFLOW_AUTH_CHECKPOINT_MS` | Cookie、LocalStorage、IndexedDB 原子保存间隔 | `300000` |
| `WORKFLOW_HUMAN_VERIFICATION_TIMEOUT_MS` | 可见模式人工验证等待时间；`0` 为无限等待 | `0` |
| `WORKFLOW_SHOP_START_STAGGER_MS` | 多店铺启动错峰间隔，避免共享 OMS/TMS 同时登录 | `30000` |
| `PDD_TEMP_SCREENSHOT_DIR` | 临时截图目录，必须位于 `WORKFLOW_DATA_DIR` 内 | `<数据目录>/tmp/tms-logistics-work-orders` |
| `PDD_RECAPTURE_EVIDENCE` | 明确设为 `true` 时覆盖重截当前订单 | `false` |
| `PDD_STATE` | 登录状态文件 | `pdd-auth.json` |
| `PDD_PROGRESS` | 当前店铺业务进度文件 | `<WORKFLOW_DATA_DIR>/state/workflow-progress.json` |
| `JEOMS_ACCOUNT` | OMS 登录账号，仅在登录状态失效时使用 | 无 |
| `JEOMS_PASSWORD` | OMS 登录密码，仅在登录状态失效时使用 | 无 |
| `JEOMS_STATE` | OMS 登录状态文件 | `jeoms-auth.json` |
| `OMS_RECHECK` | 设为 `true` 时复查当前保存订单的 OMS 结果 | `false` |
| `TMS_ACCOUNT` | TMS 登录账号，仅在登录状态失效时使用 | 无 |
| `TMS_PASSWORD` | TMS 登录密码，仅在登录状态失效时使用 | 无 |
| `TMS_STATE` | TMS 登录状态文件 | `tms-auth.json` |
| `TMS_TEMP_SCREENSHOT_DIR` | TMS 回传截图目录，必须位于 `WORKFLOW_DATA_DIR` 内 | `<数据目录>/tmp/pdd-work-order-replies` |

账号、密码、验证码和 Cookie 不得写入 `shops.config.json`、源代码、Markdown、日志或 Git。`pddSecretPrefix` 只保存环境变量前缀，不保存值。启动器会移除其他店铺的拼多多 Secret，只向当前子进程注入对应账号密码。

## 4. 主流程

### 4.1 启动浏览器

1. `run-shops.mjs` 读取非敏感店铺配置，为每个启用店铺启动独立子进程。
2. 子进程获取 `<店铺目录>/locks/workflow.lock`；同一店铺禁止重复启动，其他店铺不受影响。
3. 每个子进程单独调用 `chromium.launchPersistentContext()`，配置目录为 `<WORKFLOW_DATA_DIR>/browser-profile`；禁止任意两个店铺共享 Browser、Context 或配置目录。
4. 每个店铺创建并长期维护 `pddPage`、`omsPage`、`tmsPage` 三个基准标签页；进入后续系统时切换基准页，基准页不跨系统跳转。
5. “立即处理”如果弹出新拼多多标签页，将其登记为 `derivedTabs` 中的工单详情页；如果当前页跳转，则恢复 PDD 基准页到工单列表并在新派生页继续详情处理。派生页完成后关闭，三个基准页和登录态继续保留。
6. `WORKFLOW_BROWSER_MODE=headed` 启动本地可视化 Chromium；`server-headed` 在服务器 Xvfb 中保持 `headless:false`，通过仅限 SSH 隧道的 noVNC 维护。
7. 使用全局 `slowMo`，让每条 Playwright 指令默认间隔 4 秒。
8. 拒绝拼多多的 `local-network-access` 原生权限提示，效果等同点击右上角 `X`，不点击“允许”。
9. `headed` 和 `server-headed` 在工单完成、队列为空、验证码、人工复核或普通异常时都不主动关闭浏览器。只有明确停止服务或收到终止信号时才保存认证并关闭。
10. 启动器按店铺间隔 30 秒错峰启动，避免共享 OMS/TMS 账号同时登录；若单个店铺子进程异常退出，只延迟重启该店铺，其他店铺浏览器不受影响。systemd 负责启动器级异常恢复。

### 4.2 登录和会话恢复

1. 每个店铺只加载自己目录中的 `pdd-auth.json`、`jeoms-auth.json` 和 `tms-auth.json`。
2. 登录状态失效时才读取 `PDD_ACCOUNT` 和 `PDD_PASSWORD` 完成账号登录。
3. 登录状态失效且未注入账号密码时，在当前可视化浏览器等待人工登录；成功后重新保存 `pdd-auth.json`，并返回原工单详情继续，不重新领取工单。
4. OMS 或 TMS 登录状态失效时，只在当前店铺浏览器对应标签页恢复；即使使用相同 OMS/TMS 账号，也不得共享另一个店铺的认证文件。
5. 开始取单前依次恢复 OMS、TMS、PDD，并确认三个标签均进入登录后的业务页；实际 URL 写入 `systemTabs`，不得保留 `about:blank`。
6. 持久化上下文生成的初始空白页按固定顺序绑定到 PDD、OMS、TMS；导航先提交文档再等待 DOM，页面加载慢时继续使用已提交 URL。`browserUrl` 和 `currentUrl` 与 PDD 标签同步保存，监控不使用旧空白值。
6. 不做 OMS/TMS 周期刷新。OMS 是异步 SPA：导航完成后必须等待 Loading 消失并确认可见业务菜单或控件；如果限定时间内仍卡在 Loading，只允许执行一次受控恢复导航，之后保存诊断并暂停，不无限刷新。每 5 分钟及关键里程碑原子保存 Cookie、LocalStorage、IndexedDB，认证文件权限固定为 `600`。
7. 出现短信验证码、图形验证码、滑块、扫码或安全验证时，立即暂停当前店铺后续业务操作，不自动填写或绕过；可见模式无限等待人工完成，并在同一页面自动续跑。

### 4.3 选择工单

选择规则按以下优先级执行：

1. 设置了 `PDD_ORDER_NUMBER`：在工单列表填写订单编号并点击“查询”，等待包含该订单号的结果行。
2. 未设置 `PDD_ORDER_NUMBER`：按 `PDD_WORK_ORDER_TITLE` 精确选择第一张目标待处理工单，当前允许值为“订单问题：在途无理由退款处理”。
3. 在目标行点击“立即处理”，兼容当前页跳转和新标签页两种打开方式。
4. 进入详情后读取订单编号；若指定了订单号但详情编号不一致，立即暂停，禁止处理错误工单。
5. 一单完成后将完整进度归档到 `state/completed-work-orders/<订单编号>.json`，清空当前订单字段并返回待处理列表选择下一单。
6. 已归档订单加入跳过集合。没有目标工单时记录 `queue-empty-waiting`，保持三个标签和浏览器，每 5 分钟重新查询。
7. 设置 `PDD_ORDER_NUMBER` 时仍为单订单模式：完成指定订单后保持浏览器，不领取下一单。

完成确认优先使用详情页 `【已完结】`。提交后未显示完结时，回到待处理列表按完整订单号连续查询两次；两次均不存在时记录 `confirmationMethod=absent-from-pending-list`，仍存在则转人工且禁止重复提交。

### 4.4 保存订单编号

进入工单详情后，必须先完成以下动作，再进行物流或其他系统操作：

1. 从“订单编号”或“订单号”字段读取订单编号。
2. 写入当前店铺 `state/workflow-progress.json` 的 `orderNumber`，同时强制保存 `shopId`。
3. 同时保存 `detailUrl` 和状态 `order-number-captured`。
4. 后续 JEOMS 或其他系统直接读取该订单编号，不依赖系统剪贴板，也不重复打开拼多多页面。

### 4.5 物流分析

1. 点击“发货物流”。
2. 如果存在“全部展开”或“展开全部”，先展开完整轨迹。
3. 读取快递公司、快递单号、收货地区、所有带 `【城市】` 标签的记录，以及商家发货、揽收、中转、派件、签收等完整物流节点。
4. `traceRecords` 只保存带城市标签的记录，按时间从早到晚排列；`timelineRecords` 保存所有可识别物流节点，也按时间从早到晚排列。
5. 最早一条带城市标签的记录作为发货城市 `originCity`。
6. 最新一条带城市标签的记录作为当前城市 `latestCity`，并继续保存为 `latestTrace`。
7. `latestCity` 与 `originCity` 不同时，`outsideOriginCity` 为 `true`；相同时为 `false`。没有城市节点时三个城市判断字段分别为 `null`，但不阻止阶段判断。
8. 基于 `timelineRecords` 生成 `stageAnalysis`：
   - 待揽收阶段：以最早“商家已发货/通知快递取件”为起点，严格超过 24 小时仍无揽收时，物流问题为“超时未揽收”。
   - 揽收后初期阶段：已有揽收但没有后续运输记录，严格超过 24 小时无更新时，物流问题为“超时未更新”。
   - 中转运输阶段：最后运输节点不超过 24 小时为“运输正常”；超过 24 小时但未达到地区阈值为“常规途中无更新”，物流问题为“途中无物流更新”。
   - 普通地区满 72 小时、偏远地区满 120 小时无更新为“超期无更新”。新疆、西藏、内蒙古、青海、甘肃、宁夏属于偏远地区。
   - 超期时，邮政、中国邮政或 EMS 的物流问题为“拦截退回”，其他快递为“丢件”。
   - 最新轨迹包含派件、派送、投递中等关键词，或当前城市等于收货城市时进入“末端派件阶段”；只有明确派件后严格超过 24 小时无更新且未签收时，物流问题才为“催件”。
   - 最新轨迹显示已签收、签收成功、已妥投、已代收，或出现“已送达，签收人：……”时，按已确认业务规则进入“签收异常阶段”，物流问题为“签收未收到”。
9. 阶段判断使用中国标准时间解析轨迹时间，输出参考节点、已过小时数和实际使用的阈值；页面轨迹无论正序或倒序都先统一排序再判断。
10. 将城市判断和阶段判断共同写入同一个 `logisticsAnalysis`；截图成功后拼多多阶段才更新为 `pdd-flow-complete`。OMS 后续读取并保留这份完整对象。

示例：订单 `260723-181592409660559` 最早城市记录为“衡水市”，因此发货城市是衡水市。

### 4.6 拼多多临时证据截图

1. 截图前确认详情页订单编号与当前进度中的订单编号一致。
2. 点击“发货物流”；存在“全部展开/展开全部”时先展开完整轨迹。
3. 从“订单信息”标题向上寻找第一个同时包含订单信息、售后信息、收货信息和物流轨迹的祖先容器，只截取该右侧容器。
4. 不点击“查看手机号”“查看姓名和地址”，收货人、手机号和地址保持页面默认脱敏状态。
5. 截图瞬间隐藏容器外遮挡内容的固定顶栏，完成后立即恢复；不使用剪贴板、操作系统截图或坐标裁剪。
6. 同一订单固定覆盖 `<数据目录>/tmp/tms-logistics-work-orders/<订单编号>.png`，避免重复文件。
7. 写入后校验 PNG 文件签名、宽高、大小、可见像素及像素差异；任一验证失败则暂停，不进入后续系统。
8. 元数据写入 `pddEvidenceScreenshot`，相对路径以 `WORKFLOW_DATA_DIR` 为基准，成功状态为 `ready`。
9. 重启时，`ready` 且文件和元数据验证一致则直接复用；元数据存在但文件缺失或损坏时返回已保存的详情页重截。
10. TMS 上传失败、提交失败、查重冲突、验证码或 TMS 行截图失败时，临时 PNG 保持 `ready`。
11. 只有 TMS 工单创建响应返回 `ticketId/ticketNo`，且目标行截图通过验证后，才删除该 PNG 并把状态更新为 `deleted`。

### 4.7 OMS 订单分析

1. 拼多多阶段完成后读取当前店铺进度中的 `orderNumber`，不使用系统剪贴板。
2. 切换到当前店铺浏览器的 OMS 标签页；优先复用当前店铺的 `jeoms-auth.json`，失效时通过 `JEOMS_ACCOUNT` 和 `JEOMS_PASSWORD` 登录。
3. 出现验证码时停止自动操作，保留浏览器并等待人工输入和登录，不自动识别或绕过。
4. 点击顶部“订单”，再点击其可见子菜单中的“订单管理”。
5. 出现“点击这里也可搜索数据哦”绿色引导时，点击 `.tips-wrapper` 右上角 X 关闭；其他无关提示弹窗也点击右上角 X。订单详情弹窗属于业务窗口，不关闭。
6. 将拼多多订单编号填写到页面“订单编号/交易号/配货单号”搜索框并点击“搜索”。
7. 查询结果使用 AG Grid 当前订单行：
   - `tradeId` 是拼多多订单编号。
   - `tags` 是下方表格中的已有标记，只读取/点击这一格。
   - 忽略页面上方工具栏“标记”按钮，该按钮用于创建或批量添加标记。
   - `salesOrderCode` 是 OMS 订单号；存在多行时使用第一行。
8. 点击 `tags` 单元格后，只分析当前订单已有标记。对“低值品、低价品”等做模糊匹配；对“补发、补发单、补单、补寄、重发、补”等做模糊匹配。
9. 点击第一行 `salesOrderCode`，在订单详情弹窗点击“发货信息”。
10. 按发货信息表格的商品行顺序读取发货仓库；多行出现不同仓库时固定使用第一行的仓库，并保留全部候选用于审计。随后做仓库关键词匹配：`简卓`、`众邦`、`铭如`、`瞳琪`、`捷佑`、`亿哈`、`筑越仓`。
11. 将结果写入 `omsAnalysis`，输出“发货仓库、是否是低值品、是否是补发单”。

### 4.8 TMS 物流工单与回传截图

1. 进入 TMS 前校验订单编号一致，并要求 `timelineRecords`、`stageAnalysis`、快递公司、OMS 发货仓库和低值品结果完整；旧进度缺少完整物流时先返回拼多多重新分析和截图。
2. 仓库和快递使用 NFKC、忽略空格/标点及“仓/仓库”后缀的包含匹配：筑越仓允许任意已识别快递；简卓、众邦、铭如排除邮政/EMS；捷佑排除中通、顺丰、邮政/EMS；瞳琪、亿哈、其他、缺失或多重匹配转人工。
3. 低值品优先选择“丢件”，备注“低值品，按丢件处理”。非低值品按 `stageAnalysis` 映射为拦截退回、揽件无下文、途中无物流更新、丢件、催件或签收未收到；正常运输或证据不足转人工。
4. 使用当前店铺浏览器的 TMS 基础标签进入“智能工单管理 -> 物流快递工单 -> 客服登记”。已登录且处于业务页时直接复用，不因健康检查重复导航。创建前按完整交易号查询；若已有唯一记录，先核对订单、运单号、发货仓库和责任快递，全部一致时复用并继续截图，不一致或无法唯一确认时转人工，禁止重复创建。
5. 新建窗口填写订单号并按 Enter，必须出现“查询成功，已自动填充订单信息”，且交易号、仓库、运单号、责任快递均与当前进度一致。
6. 通过客服附件的 HTML 文件输入框上传拼多多 PNG，等待 `/api/logistics/files` 成功响应和页面缩略图；不使用剪贴板或操作系统文件窗口。
7. 点击“提交并新建”，等待 `/api/logistics/tickets` 成功响应、`ticketId/ticketNo` 和“创建成功，请继续新建”。
8. 关闭已重置的新建窗口，按完整交易号筛选并只复用进度中已保存标识对应的行。
9. 所有成功创建的 TMS 工单都必须从目标数据行的“交易号”列左边到“客服备注”列右边生成 PNG，不包含表头、操作、任务状态、工单号或附件列；文件保存为当前店铺的 `tmp/pdd-work-order-replies/<订单编号>.png` 并进行 PNG 和非空像素验证。
10. TMS 行截图初始写入 `tmsEvidenceDisposition`：`usage=pending`、`status=ready`。TMS 行截图成功后删除已上传的拼多多 PNG，流程进入 `awaiting-pdd-resolution`。

### 4.9 返回拼多多并完成工单

1. 切回当前店铺的 `pddPage`；页面不在详情时使用已保存 `detailUrl` 恢复，不重新领取工单。
2. 详情标题统一去除空格、标点和“订单问题：”前缀；“在途无理由退款处理”和完整标题视为同一类型，其他类型仍转人工。进入详情后必须确认订单号和工单详情/服务进度/订单信息等内容已渲染；空白或 Loading 页面最多按保存的 `detailUrl` 恢复一次，仍未就绪则保存诊断并暂停。
3. “消费者申请退款后提示拦截”等工单若先显示唯一可见的 `我已知晓`，自动点击该入口并等待正式处理表单渲染；该动作只确认已阅读平台提示，不作为提交结果或工单完结证据。
4. 核对页面订单号、目标工单类型和 TMS 保存结果。要求 TMS `ticketId/ticketNo` 已创建，TMS 截图为 `ready` 且与当前订单一致。
5. 如果详情已经显示“【已完结】”且订单号一致，直接记录成功并清理/归档，不选择处理选项、不上传或重复提交。
6. 处理结果：已发货无轨迹退款完成物流交接选择后，在四选一页面选择“同意退款”并直接提交，不再进入订单详情补写备注；在途无理由退款保持 OMS/TMS 前置流程不变，返回拼多多后按 `已同意退货退款`、`同意退款`、`同意消费者退款申请` 的可见顺序选择。目标退款选项与收货状态、拦截进度或消费者协商选项同时出现时仍优先选择目标退款选项；若平台用明确失败回执确认当前退款选项不适用且没有产生业务结果，则记录该回执并继续下一个可见退款选项，进程中断后的合法续跑也只返回拼多多，不重复 OMS/TMS。只有平台明确返回“未发货”才进入发货等待，不能仅凭错误码 `190001` 判断未发货。三个退款选项都未出现时才继续原有页面阶段，并按 TMS 回执选择拦截进度。
7. 只有选择 `快递还在拦截中` 后才进入消费者协商等待；满 12 小时仍无回复时选择 `消费者超12小时未回复`。该续跑只返回拼多多，不重跑已经完成的 OMS/TMS；其余协商结果不自动猜测。
8. 第二组选项实际出现时选择“主观原因不想要”；出现该组但找不到此选项时转人工。
9. 提交前写入 `pddResolutionDecision` 和 `pddResolutionSubmission.status=submitting`，随后自动点击“提交”；存在最终确认弹窗时核对预期处理结果后点击确认。
10. 只有页面明确显示“【已完结】”，订单号一致且“处理情况”与决策一致，才写入 `pddResolutionSubmission.status=succeeded`。重启发现页面已按预期完结时恢复成功，禁止重复提交。
11. 在途无理由退款当前不使用 TMS 截图，TMS 截图标记 `usage=unused`。拼多多尚未完结时必须保留；确认完结后删除 PNG，并把截图和生命周期状态更新为 `deleted`。
12. 未来其他工单上传 TMS 截图成功时标记 `usage=used`；上传失败、拼多多失败、人工复核、验证码或完成状态不确定时均保留本地 PNG。

## 5. 异常分支

### 平台限流

- 检测文字：“操作太过频繁，请稍后再试”。
- 写入状态 `rate-limited`、当前阶段、URL 和重试次数。
- 默认等待 60 秒后只重试一次。
- 再次限流则暂停当前店铺；`headed`/`server-headed` 保持浏览器和三标签，`headless` 保存诊断后退出。

### 人工验证

- 检测安全验证、验证码输入框、短信验证码或滑块提示。
- 本地有界面模式将浏览器置于前台；服务器无头模式保存诊断截图和 URL。
- 写入状态 `human-verification-required`、当前阶段和 URL。
- 在运行日志中明确提示用户，停止后续自动操作；不得绕过验证。

### 数据异常

- 30 秒内找不到目标工单：暂停并记录错误。
- 详情订单号与指定订单号不一致：暂停，禁止继续。
- 物流尚未产生城市记录时，城市字段保持 `null`，继续依据商家发货、揽收等实际节点做阶段判断，不猜测城市。
- TMS 准入不满足、字段冲突、未知重复工单、正常运输或证据不足时写入 `manual-review-required`，停止且不点击任何“转人工”按钮。
- TMS 上传、创建或截图失败时保留拼多多 PNG；进度中已有本流程 `ticketId/ticketNo` 时只恢复截图，不重复建单。
- 三店连续运行时不启用 OMS/TMS 周期刷新；每次实际操作前只检查当前标签是否仍为登录后的业务页，登录失效或页面崩溃才恢复对应系统。
- 受控重跑保留当前订单详情地址，清除旧物流、OMS 和截图元数据后重新读取拼多多物流；已有 TMS 工单按字段核对后复用，完成归档后自动领取下一单。
- 拼多多最终处理选项不唯一、工单状态不是待处理/已完结、完成结果与决策不一致时转人工，并保留 TMS PNG。
- 一个店铺出现验证码、限流或人工复核只暂停该店铺子进程，不修改或关闭其他店铺浏览器。
- `headed`/`server-headed` 保留当前浏览器和登录会话；`headless` 保存状态和诊断后退出。
- 单个 renderer 标签崩溃时，在同一 BrowserContext 中重建该业务标签并恢复原 URL，最多自动恢复 3 次；不得关闭其他店铺浏览器或丢弃认证状态。

## 7. 运行方式

校验代码、业务规则和多店铺配置，不启动浏览器：

```powershell
npm test
```

同时启动所有启用店铺：

```powershell
npm start
```

只启动一个已配置店铺：

```powershell
node run-shops.mjs --shop=panapopo-medical-device
```

店铺账号通过 `shops.config.json` 中的 `pddSecretPrefix` 对应环境 Secret 注入。例如前缀为 `PDD_MEDICAL_DEVICE` 时，启动器读取同名前缀的 `_ACCOUNT` 和 `_PASSWORD`；文档不记录具体值。未注入时，本地有界面模式允许在该店铺浏览器中人工登录。`headed` 运行后不要终止 Node 或关闭浏览器，除非用户明确要求退出。

Ubuntu 24.04 服务器常驻运行：

```bash
export WORKFLOW_BROWSER_MODE=server-headed
export WORKFLOW_DATA_ROOT=/var/lib/pdd-workflow
node run-shops.mjs
```

首次部署 Chromium 和系统依赖：

```bash
npx playwright install --with-deps chromium
```

生产部署使用 `deploy/` 中的 Xvfb、Openbox、x11vnc、noVNC 和工作流 systemd 模板。noVNC 只监听 `127.0.0.1`，必须通过 SSH 端口转发维护，不得在公网或云安全组开放 5900/6080。CentOS 7 不直接运行当前 Node/Playwright；生产目标为 Ubuntu 24.04。

启动器要求三店铺拼多多账号以及共享 OMS/TMS 账号的十项 Secret 全部存在。Windows 会在进程变量缺失时读取当前用户级环境变量；只记录 `secret-configured`，不输出值。Linux 使用 systemd Secret 或权限为 `600` 的环境文件。验证码出现后 `server-headed` 保存诊断并无限等待，人工通过 noVNC 完成后自动续跑。
